# 代码风格规则

## 技术栈

1. Flutter 业务与 UI 统一使用项目当前的 Dart SDK、Flutter、Material 3 和 `flutter_riverpod`。
2. 摄像头优先复用 `camera` 及 `core/camera` 现有封装，MQTT 复用 `mqtt_client` 与 `core/mqtt/mqtt_service.dart` 中的现有抽象和实现，本地存储复用 `shared_preferences` 相关抽象。
3. Android 平台层使用 Kotlin、Gradle Kotlin DSL、Java/JVM 17 与现有 AndroidX Camera 依赖。
4. H265 推流优先复用现有 MediaCodec、RKMPP 与 RTSP/TCP 链路，不并行引入第二套摄像头、编码或推流框架。
5. 新增实现优先基于现有技术栈；引入新依赖前先确认现有能力无法满足，并说明包体、权限、ABI、生命周期与维护成本。

## 通用要求

1. 遵循空安全与静态类型，避免无必要的 `dynamic`、强制类型转换和空值断言。
2. 保持类和函数职责单一，优先选择直观实现，不为一次调用制造多层抽象。
3. 新增或实质修改的类、函数和方法使用对应语言惯例编写中文文档注释；注释说明职责、输入输出、生命周期或失败边界，不复述语法。
4. 复杂业务判断、异步竞态、线程切换、资源所有权、协议字段和兼容性处理添加简洁的中文行内注释。
5. 默认使用 ASCII 标识符；中文文档、界面文案、日志业务说明和既有资源名除外。
6. 不为当前任务顺手格式化、重排、重命名或重构无关代码。
7. 不编辑生成文件、构建产物或二进制库；必须更新生成物时，先修改其事实来源并使用明确的生成流程。

## Dart 命名、导入与格式

1. 文件和目录使用小写 `snake_case`，类型和扩展使用 `UpperCamelCase`，变量、参数、方法和命名构造函数使用 `lowerCamelCase`。
2. 页面文件使用 `_page.dart`，对话框、卡片、列表项等组件使用 `_dialog.dart`、`_card.dart`、`_tile.dart` 等职责后缀；DTO 使用 `_dto.dart`，Repository 实现使用 `_repository_impl.dart`。
3. Repository 接口不添加 `I` 前缀，不使用无业务含义的 `index.dart`，不使用 `part/part of` 拼接页面私有实现。
4. 跨目录导入使用 `package:smart_cabinet/...`；同一小目录内可以跟随现有相对导入方式，但避免脆弱的多层 `../../`。
5. 导入顺序保持为 Dart SDK、Flutter/第三方包、项目包，并由空行分组；删除未使用导入。
6. 优先使用不可变对象、`final`、`const` 构造和 `const` Widget；只有确实需要重新赋值时才使用可变变量。
7. 让 `dart format` 决定排版，不手工对齐空格；只格式化本次实际修改的 Dart 文件。

## Flutter 与页面实现

1. 页面和组件遵循现有 Widget 写法，优先组合小组件，不把数据访问、设备协议或大量业务分支直接塞进 `build()`。
2. 优先复用 `AppTheme`、`TerminalShell`、现有业务 Widget 和 `shared/widgets/` 中的通用反馈组件，不为单页建立新主题或提示体系。
3. 柜机界面需要兼顾固定横屏、紧凑尺寸和长文案；新增布局应检查溢出、滚动、触控区域、弹窗高度与多语言扩张。
4. 页面跳转使用 `AppRoutes` 与 `AppRouter` 的既有命名路由，不在多个页面复制字符串路由。
5. 异步操作返回后访问 `BuildContext`、调用 `setState` 或跳转前，检查 `mounted`；可能被新请求覆盖的任务使用 generation、取消或等价机制防止旧结果回写。
6. `Timer`、Stream subscription、Camera controller、Provider container、线程执行器及其他可释放资源必须由明确所有者在生命周期结束时释放。
7. 不在 Flutter UI isolate 执行长时间同步 I/O、编码、网络等待或 CPU 密集任务。
8. 用户操作需要防重复提交；启动、停止、重试和页面销毁路径应保持幂等。

## Riverpod 与状态

1. Riverpod 用于需要共享、替换、缓存或测试注入的依赖和状态；Widget 私有瞬时状态继续使用 `StatefulWidget`。
2. 应用级 Provider 放在 `app/` 或对应 `core` 能力附近，仅单个 Feature 使用的 Provider 放在该 Feature 内。
3. 不为局部开关、输入框或一次性动画强行创建全局 Provider。
4. Provider 的创建、刷新和销毁边界必须明确；异步 Provider 需要暴露加载、成功和失败状态，不能静默吞掉错误。
5. 测试通过 `ProviderScope` override、抽象接口或构造参数替换外部依赖，不在测试中连接真实 MQTT、摄像头或 Android 通道。

## 数据、网络与存储

1. 页面数据优先遵循 `Page/Controller -> Repository -> DataSource -> HttpClient`，外部响应遵循 `JSON -> DTO -> Domain Entity -> Page`。
2. DTO 贴近外部协议，Domain Entity 表达业务语义；不要把 JSON Map、平台通道 Map 或 DTO 直接传到 Widget 树深处。
3. Repository 实现负责组合数据源、映射对象和统一错误，不承载具体页面布局或导航逻辑。
4. 模拟响应集中维护，不在页面、测试和 Repository 多处复制同一组业务数据。
5. 修改接口字段时同步检查模拟数据、DTO 解析、Entity、Repository 映射、空值兼容和调用方测试。
6. SharedPreferences key 和序列化规则通过现有存储抽象集中管理；读取失败、旧版本数据和迁移路径必须有确定行为。
7. 网络、MQTT 和平台调用设置合理的超时、重试与断线行为。重试必须有边界，不能形成无限快速循环。

## 身份、任务与柜门安全

1. `verifiedFactors` 使用 `Set<IdentityFactor>` 保存已通过的不同身份因子；正式模式下账号密码、重复验证或 UI 步骤数量都不能代替人脸、指纹与 NFC 中的任何一项。唯一例外是 `AppConfig.current.isTestMode == true` 的账号登录测试旁路，且正式部署前必须关闭。 测试模式的人脸模拟认证必须在 UI 中明确标识，不得使用“已提交后端”等真实成功表述。
2. 身份资料状态通过 `OperatorIdentityProfileStatus` 和现有协调器迁移。任何同步、校验、报备或录入失败都不能进入任务中心；录入完成后清空当前流程并回首页重新登录。
3. 路由层和 Repository 层保持双重门禁。任务 Repository 是最终授权边界，每个公开读取或变更动作都重新检查人脸、指纹与 NFC 三项身份因子、操作员机构和任务机构；读取任务时还必须拒绝删减、增加、重排或非连续完成的步骤集合。
4. 取件码和飞检码分别使用专用 Repository 入口，并校验任务类型、当前步骤和码值。通用步骤完成方法不得接受这两类步骤，失败路径不得保存任何新状态。
5. 分箱、授权箱格和开门使用最新任务状态，并校验 `account.organizationId == task.organizationId == slotBinding.organizationId`，同时校验当前证件门号、绑定门号和请求门号一致。
6. 存证、取证、借证和还证保持各自业务状态。借证不能只复制取证文案后声称形成闭环；只有平台借出记录和还证核销成功才能完成真实借还闭环。
7. 盘点使用箱格级模型和专用 Repository 动作，不把同一箱格中的证件套入普通逐项流程重复开门。抽盘计划由平台生成；比例按箱格计算，指定证件逐个唯一存在并扩展到所在箱格的全部证件；全部预期证件必须属于计划箱格，活动箱格、验证码状态和缓存绑定必须自洽。
8. 盘点箱格的灰、蓝、橙、浅绿、绿、红状态映射集中维护，并同时显示“无需盘点、待盘、盘点中、部分完成、正常、异常”等文字或图标，不仅依赖颜色表达。
9. RFID 扫描由 Repository 原子记录：预期 RFID 标记正常，非预期 RFID 新增溢余，同一 RFID 重复扫描幂等。只有匹配柜门的关门确认才能把剩余预期证件标记缺失；缺失件的放回状态显示未发现。
10. 常规盘点默认不逐份拍照。异常留痕仅在平台任务要求时触发，优先拍摄箱格全景；临时照片在上传成功、重试终止、页面销毁和生命周期切换时按明确策略清理，不能写入普通日志或无保护存储。
11. 页面默认复用应用级 `globalCabinetDoorGuard`，只有测试可以通过构造参数注入独立实例。开门前先完成 Repository 复核，再为本次开门周期创建唯一 `operationId` 并请求互锁，最后才调用真实设备。
12. 柜门超时只报警，不自动调用 `markClosed`，也不触发盘点缺失判定；页面销毁、异常和导航同样不得释放互锁。只有 `activeDoorNo` 与 `operationId` 都匹配的明确关门确认可以释放，真实接入后以门磁为准。开门响应异常时先对账，无法确认则人工关门并通过 Repository 回退后再释放。
13. 门未关闭时禁止退出、返回任务中心、关闭盘点明细或打开第二柜门。无任务退出 Timer 在安全条件失效时隐藏或重置，并在页面销毁时取消，避免旧回调继续导航。
14. 人脸临时照片和证件异常照片都必须遵守最小留存原则；不得把口令、飞检码、取件码、人脸原图、指纹模板、证件原文或异常照片路径写入日志和普通本地存储。
15. 模拟扫码、模拟 OCR、UI 关门确认和内存状态必须在命名、文案和交付说明中标明模拟边界，不能冒充真实设备读数或平台成功结果。

## 多语言、主题与用户反馈

1. 固定业务文案通过现有多语言入口读取，并提供准确的中文兜底；key 使用清晰的业务前缀。
2. 新增或修改文案同步维护简体中文、繁体中文、英语和日语，不用机器占位文本冒充已完成翻译。
3. 颜色、字号、圆角和间距优先复用 `AppTheme` 或同级现有样式，不散落新的魔法值体系。
4. 错误提示保留底层或后端返回的具体原因，再补充用户可执行的恢复动作；不要用笼统的“操作失败”覆盖更有价值的信息。
5. 需要记录的异常进入 `AppLogger`；硬件异常优先复用现有恢复建议和全局覆盖层，避免每个页面自定义不同口径。
6. 日志不得写入口令、令牌、人脸原始数据、身份证件内容或其他敏感信息。

## Android、Kotlin 与 MethodChannel

1. Kotlin 代码遵循现有 Android/Kotlin 风格，类使用 `UpperCamelCase`，函数和属性使用 `lowerCamelCase`，常量放入 `companion object` 并使用 `UPPER_SNAKE_CASE`。
2. `MainActivity` 只承担 Flutter 引擎接入和顶层生命周期编排；持续增长的摄像头、编码、RTSP 或设备逻辑放入 `kiosk/` 下职责明确的类。
3. MethodChannel 方法名、参数键和返回类型视为跨语言 API。Dart 与 Kotlin 任一侧改变时必须同步另一侧，并为成功、缺参、平台异常和不支持方法提供确定结果。
4. Android 主线程只处理 UI、生命周期和必须的系统调用；相机读取、编码、网络发送和其他阻塞工作使用现有执行器或后台线程。
5. 新建 Handler、Executor、Camera session、Codec、Socket 或 Server 后，必须在停止、异常和 `onDestroy` 路径释放；关闭操作保持可重复调用。
6. 不静默捕获平台异常。内部日志保留技术原因，对 Flutter 层返回稳定错误码和可理解信息。
7. 修改 Manifest、权限、Device Admin、Kiosk 或设备所有者配置时，说明安装、授权和真机验收影响。

## C++、JNI 与 RKMPP

1. JNI 导出函数签名必须与 Kotlin `external` 声明一致；修改包名、类名、方法名、参数或返回值时同步核对双方。
2. 访问 RKMPP 动态符号、上下文、Buffer、Frame、Packet 和编码配置时，检查空指针、返回码、长度与所有权。
3. 共享编码器状态继续受互斥保护；不要在持锁期间执行无界等待，也不要让失败路径遗漏解锁或资源回收。
4. YUV 格式、stride、宽高、码率、GOP 和时间戳属于链路契约，修改时同步核对 Camera2 输入、编码器配置、RTSP 封包与播放器兼容性。
5. C++ 源码改动不能以普通 APK 构建成功作为 native 已更新的证据；必须确认实际重建并打包了目标 `arm64-v8a` `.so`。
6. 不直接编辑、伪造或无依据替换 `jniLibs/` 中的二进制文件。

## 测试与验证

1. 行为变更应新增或更新最接近该行为的测试，测试名称描述用户行为或失败场景。
2. 单元测试不依赖执行顺序、真实网络、真实 MQTT broker、真实摄像头或固定本机路径。
3. Widget 测试覆盖关键入口、交互、加载、失败、多语言和布局；需要异步推进时使用可控 pump，不使用真实 sleep。
4. MethodChannel 测试显式安装和清理 mock handler，避免测试之间泄漏全局状态。
5. 修复竞态、重试、资源释放或错误恢复问题时，至少覆盖原失败路径和重复调用路径。
6. Camera2、MediaCodec、RKMPP、RTSP、Device Owner 与 Kiosk 模式最终以目标 ARM64 设备复测为准。
7. 身份流程测试覆盖正式模式账号密码不计因子、测试模式账号登录旁路、测试模式人脸不等待摄像头或后端、人脸登录仍需三项全验、管理员与普通操作员三栏布局一致、缺少任一身份因子时拒绝、同步与异常场景仍需三项全验、录入失败重试和异常报备后重录。
8. 任务与柜门测试覆盖缺少任一身份因子时拒绝、跨机构任务与箱格拒绝、乱序步骤、错误取件码或飞检码不推进、同箱多证件只开一次门、第二柜门冲突、错误关门不释放、超时不释放且不判缺失、正常/重复/溢余 RFID、关门自动标记未扫描证件缺失、六种箱格状态、门开暂停退出，以及全部任务项完成后才允许结束。

## 编辑与验证

1. 优先提交便于审查的最小差异。
2. 可以验证时，只运行最小且相关的检查；不要为了文档改动启动模拟器、设备或开发服务器。
3. Dart 源码改动依次考虑：格式化改动文件、`flutter analyze`、相关 `flutter test <path>`，跨模块改动再运行完整 `flutter test`。
4. Kotlin 或 Android 配置改动按需进入 `android/` 后运行 `.\gradlew.bat :app:assembleDebug`；摄像头、推流或 Kiosk 改动同时列出真机验收项。
5. APK 构建优先使用 `flutter build apk --debug`。执行 release 构建时必须明确当前 debug key 签名限制，不能作为正式发布结论。
6. 日常验证不运行 `flutter clean`；只有确认缓存损坏或 native/资源产物未更新时才使用。
7. 未经用户明确要求，不运行 `flutter pub upgrade`；依赖声明变化或缺失时使用 `flutter pub get` 并检查 `pubspec.lock` 差异。
8. 不允许使用 `git worktree` 或 linked worktree 进行隔离修改；所有修改发生在当前仓库工作区。
9. 未经用户明确授权，不执行 `git add`、`git commit`、`git commit --amend`、`git push`、`gh pr create` 等 Git 写操作。
10. 当文件、构建产物、缓存、APK、日志或预编译库是否保留无法明确判断时，必须先让用户确认。
11. 不允许为了占位创建空 README、普通说明文档、空接口或空目录；仅保留入口说明、AI 规则、重要专题教程或跨模块架构决策。

## Markdown 文档

1. 项目内说明类 Markdown 文件使用中文编写，包括 README、配置教程、规则文档和工程脚本说明。
2. 技术专有名词、代码标识符、命令、API、Widget、Provider、MethodChannel、JNI、Camera2、RKMPP、RTSP 等保留英文原文。
3. 新增或修改 Markdown 文档时，中英文之间留空格，中文与数字之间留空格，中文语境使用全角标点。
4. 代码块、配置字段、通道名、接口路径和示例值不强制翻译，避免破坏可复制执行性。
5. 文档中的本机绝对路径、设备地址、进程号、签名状态和性能数据必须标明适用环境，不能写成通用事实。
